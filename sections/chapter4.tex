\chapter{Implementation and Testing}

This chapter describes the current implementation status of the \textbf{ForeSyte} AI Exam Surveillance System and the testing performed up to this iteration. The focus of this phase is on the \textbf{Admin}, \textbf{Investigator}, and \textbf{Student} portals and their supporting backend services. Computer-vision based monitoring remains a planned component and therefore is out of scope for this iteration.

\section{Current Progress}

\subsection{Front-End}

The front-end is implemented as a React-based single-page application with TypeScript, Vite, and Tailwind CSS, providing role-specific dashboards for administrators, investigators, and students.

\subsubsection*{Admin Dashboard}

The admin dashboard displays key metrics (active exams, incidents detected, students monitored, average exam duration) fetched from \texttt{/dashboard/stats}, along with activity charts, recent incidents, quick actions, and system status indicators. All components are fully integrated with backend APIs.

\subsubsection*{Investigator Portal}

The Investigator Portal provides a dedicated interface with dashboard views showing violation summaries and recent activities, plus a reports page for generating and managing incident and exam reports. All components are fully integrated with backend APIs and tested with database records.

\subsection{Back-End}

The backend uses FastAPI with PostgreSQL and MongoDB, implementing JWT-based authentication with RBAC. Key modules include the Dashboard API for aggregating statistics and the Reports API for managing report records.
\subsubsection*{Dashboard API}

The \texttt{/dashboard/stats} endpoint computes active exams, incidents detected, students monitored, average exam duration, and trends. The \texttt{/dashboard/activity} endpoint provides time-bucketed data, while \texttt{/dashboard/recent-incidents} returns the latest flagged activities. All endpoints enforce RBAC policies.

\subsubsection*{Reports API}

The \texttt{/reports} router provides CRUD operations for report metadata and endpoints for generating incident and exam reports. Note: actual file generation (PDF/CSV/Excel) is planned for future iterations; current endpoints create database records only.

\subsection{Detailed Usage}

Google OAuth 2.0 is implemented in \texttt{src/database/auth.py} using Authlib library, with endpoints \texttt{/auth/google} and \texttt{/auth/google/callback} for initiating and handling OAuth flows, and functions \texttt{oauth.register()}, \texttt{google.authorize\_redirect()}, and \texttt{google.authorize\_access\_token()} for client registration, user redirection, and token exchange. OpenCV (cv2) is used in \texttt{src/app/video\_processing/stream\_handler.py}, \texttt{processor.py}, and \texttt{src/app/live\_phone\_feeds/phone\_stream\_receiver.py} for capturing video frames from live streams and recorded videos, processing video streams for behavior analysis, and frame extraction for AI-based detection using functions such as \texttt{cv2.VideoCapture()}, \texttt{cap.read()}, \texttt{cv2.imread()}, and \texttt{cap.get(cv2.CAP\_PROP\_FRAME\_COUNT)}. PDFplumber is utilized in \texttt{src/app/seating\_plan/upload\_plan.py} and \texttt{import\_students\_from\_pdf.py} for extracting student information, parsing exam schedules and room assignments, and extracting roll numbers and student names from PDF tables through functions \texttt{pdfplumber.open()}, \texttt{page.extract\_tables()}, and \texttt{page.extract\_text()}. Requests library is employed in \texttt{src/database/api/stream\_proxy.py}, \texttt{src/app/live\_phone\_feeds/phone\_stream\_receiver.py}, and \texttt{connection\_tester.py} for making HTTP GET requests to fetch video streams, proxying video streams to frontend, and testing connectivity to phone camera endpoints using \texttt{requests.get()} and exception handlers for timeout and connection errors. Python-JOSE is implemented in \texttt{src/database/auth.py} for encoding and decoding JWT tokens for authenticated users, validating tokens in protected routes, and managing user session tokens through functions \texttt{jwt.encode()}, \texttt{jwt.decode()}, and \texttt{JWTError} exception handling.

\section{Algorithm Design}

This section summarizes the main algorithms and data flows used to support the implemented features in ForeSyte.

\subsection{Admin Dashboard Aggregation}

The Admin Dashboard relies on server-side aggregation logic to compute statistics for different time windows. The high-level algorithm for computing dashboard statistics is:

\begin{enumerate}
    \item \textbf{Determine Time Window:} Given \texttt{period} $\in \{\texttt{today}, \texttt{week}, \texttt{month}\}$, compute the current window (\texttt{start\_date}) and the immediately preceding window (\texttt{prev\_start}, \texttt{prev\_end}) for trend comparison.
    \item \textbf{Count Active Exams:} Query \texttt{Exam} where \texttt{exam\_date} is greater than or equal to the current date. Perform the same query on the previous window to obtain \texttt{prev\_active\_exams}.
    \item \textbf{Count Incidents and Students:} 
    \begin{itemize}
        \item Incidents: count \texttt{StudentActivity} records with timestamps within the current window.
        \item Previous incidents: count \texttt{StudentActivity} records within the previous window.
        \item Students monitored: count distinct \texttt{Seat.student\_id} in rooms and exams that fall inside the current and previous windows.
    \end{itemize}
    \item \textbf{Compute Average Exam Duration:} For all exams in the current window with non-null start and end times, compute the duration in minutes and average the result.
    \item \textbf{Compute Trends:} For each metric (incidents, students, exams), compute percentage change between current and previous counts, handling the edge case when the previous value is zero.
    \item \textbf{Return Structured Response:} Package all calculated values into a \texttt{DashboardStats} object and return it to the client.
\end{enumerate}

On the client side, the React dashboard:
\begin{itemize}
    \item Calls \texttt{/dashboard/stats} to populate the metric cards.
    \item Calls \texttt{/dashboard/activity} to render a bar chart comparing incidents and exams per time bucket.
    \item Calls \texttt{/dashboard/recent-incidents} to display the latest suspicious activities with relative time labels.
\end{itemize}

\subsection{Report Generation Workflow (Planned Design)}

The report generation workflow is designed to be configurable and format-agnostic. \textbf{Note:} The following describes the planned design; actual file generation (PDF, CSV, Excel) is not yet implemented in this iteration.

\subsubsection*{Incident Reports (Planned)}

\begin{enumerate}
    \item The investigator selects one or more incident IDs and chooses an export format (e.g., PDF, CSV, JSON), with options such as including video evidence links.
    \item The front-end constructs an \texttt{IncidentReportRequest} and sends it to \texttt{POST /reports/incidents}.
    \item The backend validates permissions, resolves the incident IDs into \texttt{StudentActivity} records, ensures there is an associated \texttt{Violation}, and generates a unique report filename.
    \item A new \texttt{Report} record is inserted in the database, and the API returns the report ID, file path, format, and status to the client. \textbf{In the current iteration, the actual report file is not generated; only the database record is created.}
\end{enumerate}

\subsubsection*{Exam Reports (Planned)}

\begin{enumerate}
    \item The investigator selects an exam and desired output format from the Reports Page.
    \item The front-end sends an \texttt{ExamReportRequest} to \texttt{POST /reports/exams/\{exam\_id\}}.
    \item The backend verifies the exam, aggregates its related \texttt{StudentActivity} records, ensures a linked \texttt{Violation} exists, and creates a \texttt{Report} entry in the database.
    \item The API responds with the report metadata. \textbf{The actual report file generation (PDF/CSV/Excel) will be implemented in a future iteration.}
\end{enumerate}

\subsection{Investigator Violation Review Flow}

The Investigator Dashboard is designed to give investigators a structured way to triage violations:

\begin{enumerate}
    \item Load dashboard summary counters (total violations, pending reviews, resolved today, active exams).
    \item Display a list of recent activities with type, severity, and status tags.
    \item Allow investigators to toggle the period filter to focus on \texttt{today}, \texttt{week}, or \texttt{month}.
    \item Provide a \textit{Review} action for each activity which, in the next iteration, will navigate to a detailed case view and allow updating violation status and adding investigation notes.
\end{enumerate}

\subsection{Seating Plan Upload and Processing}

The seating plan upload algorithm processes PDF files containing exam schedules and extracts room, student, and seat assignment information. The algorithm handles PDF parsing, data extraction, database operations, and visualization generation. The high-level pseudocode for this process is:

\begin{lstlisting}[language=pseudocode, basicstyle=\ttfamily\footnotesize, frame=single, backgroundcolor=\color{gray!10}, breaklines=true, breakatwhitespace=true, tabsize=2, showstringspaces=false, numbers=left, numberstyle=\tiny\color{gray}, numbersep=8pt, xleftmargin=15pt, xrightmargin=15pt, framexleftmargin=10pt, framexrightmargin=10pt, framextopmargin=5pt, framexbottommargin=5pt, rulecolor=\color{gray!50}]
START timer

READ uploaded PDF bytes
EXTRACT full text from all pages
NORMALIZE text (remove extra whitespace)

DEFINE block_pattern to detect each exam block inside PDF
FIND all exam blocks using regex

CREATE empty list: matching_exams

FOR each exam block:
    EXTRACT exam date
    EXTRACT exam time slot
    EXTRACT room number
    IF failed -> continue

    CHECK if user-specified room_no matches (if provided)
    CHECK if user-specified time_slot matches (if provided)
    IF mismatch -> continue

    EXTRACT course name + section
    EXTRACT invigilator name

    FIND all students using regex:
        serial_no, roll_no, name, seat_no

    ADD exam entry to matching_exams list:
        date, time, course, section, room, invigilator,
        student_list, total_students, uploaded_at

IF matching_exams is empty:
    RETURN "No seating plan found"

SELECT first exam -> selected_exam
STORE selected_exam in global latest_room_data

PARSE exam_date, start_time, end_time using parse_date_time()

------------------------------------
DATABASE OPERATIONS
------------------------------------

# --- EXAM ---
QUERY Exam table:
    WHERE course == selected_exam.course
    AND   exam_date == exam_date
    AND   start_time == start_time

IF exam exists:
    use existing
ELSE:
    CREATE new Exam object
    COMMIT to DB

# --- ROOM ---
Split room number into block + room_num
QUERY Room table:
    WHERE room_number == room_num AND exam_id == exam.exam_id

IF room exists:
    use existing
ELSE:
    CREATE Room with:
        room_number, block, total_seats, exam_id, camera_id
    COMMIT to DB

# --- STUDENTS + SEATS ---
FOR each student in selected_exam.students:
    roll_number = student.roll_no
    name = student.name

    QUERY Student table WHERE roll_number matches
    IF not exists:
        CREATE new Student(name, email_from_roll, roll_number)
        COMMIT

    seat_number = student.seat_no

    QUERY Seat table WHERE (room_id, seat_number)
    IF exists:
        UPDATE seat.student_id
    ELSE:
        CREATE new Seat(room_id, seat_number, student_id)

COMMIT all changes

------------------------------------
SAVE JSON EXPORT
------------------------------------

GENERATE timestamp-based filename
SAVE selected_exam as JSON file in extractions folder

------------------------------------
VISUALIZATION PROCESS
------------------------------------

LOAD CCTV frame image
LOAD seat_map.json (polygon coordinates)

CALCULATE max_column in seating plan:
    For each student seat (C#R#) 
        Extract column number
        Track the maximum found

DEFINE mapping rules based on max_column:
    if max_col == 6 -> map 6 columns to 1,3,5,6,8,10
    if max_col == 5 -> map 5 columns to 1,4,6,8,10
    else -> identity mapping

DEFINE function map_seat_to_seat_map(seat_no):
    Extract C#, R#
    Convert input col -> mapped column
    RETURN seat_map ID like seat_cXrY

CREATE:
    filled_seats = all seat IDs containing students
    student_seat_map = map seat_id -> student

FOR each seat_id in seat_map:
    IF seat_id NOT in filled_seats -> skip

    GET polygon points
    DRAW polygon in green

    FIND student assigned
    CALCULATE centroid
    DRAW student name + roll number at centroid

SAVE annotated image in extractions folder

------------------------------------
RETURN RESPONSE
------------------------------------

RETURN:
    message
    exam_date
    exam_time
    course
    room_no
    students_count
    exam_id
    room_id
    json_file path
    annotated_image path
    processing_time
\end{lstlisting}
The algorithm processes seating plan PDFs through several stages: (1) \textbf{PDF Parsing and Text Extraction}, where the uploaded PDF is read and normalized; (2) \textbf{Pattern Matching}, where exam blocks are identified using regex patterns and filtered by user-specified room number and time slot; (3) \textbf{Data Extraction}, where course information, invigilator details, and student seat assignments are extracted; (4) \textbf{Database Operations}, where Exam, Room, Student, and Seat records are created or updated; (5) \textbf{JSON Export}, where the extracted data is saved as a JSON file; and (6) \textbf{Visualization}, where the seating plan is overlaid on a CCTV frame image with student names and roll numbers annotated at their respective seat positions.
